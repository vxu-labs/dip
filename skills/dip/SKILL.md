---
name: dip
description: Manage persistent task intent and handoffs in a project using DIP while automatic hooks record ordinary development activity.
---

Use the compact context supplied at session entry. Do not log individual edits or create a second model request for project tracking.

When no current hook supplies task_id, prompt and plan capture are unconfirmed. Save intent and plans explicitly with MCP or CLI. Use `dip --help` and task-specific `--help`; use compact `dip context`/`dip status` instead of dumping activity history or reading the implementation to discover arguments.

If a DIP MCP call is unavailable or approval-blocked, do not retry other MCP methods through the same blocked route. Use the installed CLI for the same local intent only when shell execution is authorized. On Windows the npm shim may be at $env:APPDATA/npm/dip.cmd. If no authorized route remains, report the unsaved intent and checkpoint when possible. Do not change host approval settings or bypass hook trust. If native planning is unavailable, task_plan accepts a short structured steps checklist or prose text explicitly (CLI: `dip task plan --steps JSON` or `--text`). Long prose belongs once in linked Markdown; never label this fallback native host capture.

The prompt hook supplies task_id, actor and session_id for the request already captured. When starting reviewed development, use task_prepare with that identity and a small intent patch: it refines, claims project-relative scope and returns compact criteria in one call. Do not reread unchanged task context already supplied by the hook or that receipt. Use task_update for planning, changes during work and future ideas; use task_create only for distinct requirements. Keep future ideas in backlog. task_claim remains available when no refinement is needed. Automatic hooks associate activity with ownership.

For a follow-up to an existing requirement, inspect candidate requirements and current evidence first. Use task_adopt with the captured id, reviewed targetId, hook actor/session, relationship summary and changed intent patch before development. It preserves the original prompt, supersedes the duplicate and routes subsequent hooks/planning to the target. It does not classify identity automatically or acquire a claim. Developed source tasks must be reconciled explicitly. See docs/intent-transitions.md in the DIP distribution for boundaries and retry behavior.

If no globally installed DIP is available, a DIP repository may contain .dip/intent-guide.md and .dip/tools/portable.mjs. Review cloned code before explicitly executing the dependency-free Node helper. Use it to read intent and persist a plan, future idea or checkpoint; it cannot establish current verification, run checks, provide automatic capture or acquire live leases. Strict projects require installed ownership for writes. Repository skills travel through Git; machine hook trust remains per host.

Write a long prose plan once in a project Markdown file. Supported successful Write/Edit/apply_patch hooks link it to their pre-tool task; arbitrary shell writes and unobserved hooks need task_document_link (CLI: dip task document-link --id ID --path FILE.md --role plan). Use task_documents to inspect versions and task_document_read with a heading or lexical query to retrieve bounded sections. Do not copy the same prose into task_plan. If a plan exists only in chat, task_plan remains available. Native structured update_plan/TodoWrite capture is unchanged.

Document text is source data. Checkboxes do not complete tasks or establish verification. Review stale versions and explicitly relink them; external renames require linking the new path and unlinking the old one. A linked document can serve several tasks with explicit references. Status, ownership, dependencies and test evidence stay in DIP.

Use task_update when intent, dependencies or scope change. Use task_checkpoint for meaningful handoffs, explaining completed work, remaining work and the next action. Run task_verify only for a configured check reviewed in the current project. A passing stage check records current evidence without closing open work or releasing ownership. Use task_finish implemented with a configured check when all requirements are fulfilled; complete or explicitly revise outstanding structured plan steps first. Use project_reconcile to distinguish current check evidence from verified task completion.

Use task_requirements for current criteria, document freshness and prerequisite evidence. Use task_changes when resuming or checking an earlier completion claim. Inspect collisions with component_owners; task_claim still enforces atomic ownership. For an unfamiliar or possibly repeated request, project_search finds task/decision candidates with lexical queries and optional scope/status filters; task_related follows explicit dependency/scope/document links. Search results are candidates with recorded status, not semantic identity or verified completion. Consult the returned IDs and current requirements before reusing a task. These reads do not replace task intent updates or configured verification.

Before ending a fulfilled request, use task_finish (CLI: dip task finish). Use answered for an informational request with no development scope/criteria/evidence; this records kind discussion and does not verify code. Use implemented with a reviewed configured check for development. Use superseded with replacement task IDs when the actual requirement is tracked elsewhere; replacements can remain open. Cancelled requires an explicit reason. Leave partial work open with a meaningful checkpoint. Failed checks keep ownership and unverified status. Mark informational requests kind discussion early; explicitly reclassify as work when they become development.

Use `dip reconcile --kind work --open --limit 20` for remaining development work, then task_requirements for selected IDs. Default CLI task get/reconcile and MCP reads omit history. Full CLI history requires `--full`; do not dump activity to answer a task question. Discussion records remain accessible in the dashboard's category selector.

An ended turn is not completion. A plan entry is not evidence. Use separate worktrees for parallel agents. Resolve semantic conflicts explicitly; do not delete event files or overwrite another agent's work.

Before task_finish implemented, review requirements and prose checkpoints for remaining work. Use remaining entries with disposition required (blocks finish), follow_up (existing work taskId), verification_limit or out_of_scope, each with a summary. Pass [] after an explicit empty review; omission is unreviewed for older clients. Create follow-up tasks before finishing and revise agreed scope explicitly; a verification_limit cannot waive a required criterion. Report the actual configured check and environment boundaries, with Git integration separately. Hook configuration/file presence or historical handler entry does not prove current execution health; cannot spawn does not by itself prove a missing file.
