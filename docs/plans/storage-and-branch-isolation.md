# DIP: הגבלת נפח והפרדת נתונים מענפי הקוד

תאריך: 2026-11-02. סטטוס: אושר ומומש בגרסה 0.4.0. בוצעה מיגרציה ל־58 משפחות Git ו־79 עותקי עבודה זמינים, עם גיבויים ואימות נתונים. [דוח המימוש וההפעלה](../benchmarks/2026-11-02-storage-release.md) מתעד את הבדיקות, המדידות ומגבלות ההפצה. הטקסט בהמשך משמר את התכנון ואת ממצאי הבסיס מלפני המימוש; ניסוחים כגון ״מוצע״ ו״טרם מומש״ מתארים את אותו שלב היסטורי.

## ההמלצה

להפריד בין שלושה דברים: מידע פרויקטלי חשוב שנשמר לאורך זמן, פעילות תפעולית עם תקציב נפח, וקוד הפרויקט. לכל משפחת Git יהיה מאגר DIP מקומי אחד שמשותף לכל ה־worktrees, וענף נתונים יחיד בשם מוצע `dip/state` לצורך היסטוריה ושיתוף של המידע החשוב. DIP יעדכן את הענף ללא checkout וללא שינוי ה־index של המשתמש. פעילות מפורטת לא תיכנס לענפי הקוד או להיסטוריית Git כברירת מחדל.

זו המלצה לשינוי פורמט אחסון ומנגנון סנכרון. העברת `.dip/events` בשלמותה לענף נוסף תטפל בחלק מההתנגשויות, אבל תשאיר את בעיית הנפח.

## מה נמצא בפועל

ה־HEAD המקומי ב־`main` הוא `cf770f3` מ־9 באוקטובר; ה־ref המקומי `origin/main` נמצא ב־`885a0b6` מ־29 באוקטובר, 19 קומיטים קדימה. נבדקו גם הקוד והדוחות בגרסה המאוחרת, והחבילה הגלובלית המותקנת: `0.3.13-automatic.2`. לא בוצע fetch, ולכן זו הגרסה המאוחרת הזמינה מקומית, ללא טענה שנבדק מצב השרת העכשווי.

שינוי החיסכון האחרון עוסק בתהליך האוטומטי, בהפחתת קריאות ניהול, בהקשר פתיחה של עד 4,096 בתים ובתשובות ניהול של עד 1,024 בתים. הדוח מתעד ירידה של 81% בקריאות השגרתיות ו־33.9% ב־administrative payload בניסוי האחרון; יעד ה־60% נשאר להמשך. אלה מדדי תעבורה למודל, לא מדדי אחסון. מסמך התהליך קובע במפורש: `Full ledger data is unchanged`.

אסמכתאות מהגרסה המאוחרת: [החוזה](https://github.com/vxu-labs/dip/blob/885a0b68a43073515ea5c29fa11f4ea8157401eb/docs/automatic-workflow.md), [דוח ההשוואה](https://github.com/vxu-labs/dip/blob/885a0b68a43073515ea5c29fa11f4ea8157401eb/docs/benchmarks/automatic-workflow-report.md), [החלטת המיזוג וההפעלה](https://github.com/vxu-labs/dip/blob/885a0b68a43073515ea5c29fa11f4ea8157401eb/docs/benchmarks/2026-10-29-merge-decision.json). הדוח כולל טקסט היסטורי על חסימת rollout; החלטת 29 באוקטובר מתעדת את האישור המאוחר להפעלה למרות דחיית יעד ה־payload.

נמדדו ספריות `.dip` של פרויקטים הרשומים ב־runtime, ללא קריאת תוכן השיחות. יחידות הטבלה עשרוניות: MB = מיליון בתים, GB = מיליארד בתים. נתוני הקצאה נלקחו מ־`st_blocks * 512`; הם אינם מדידה של צריכת APFS בלעדית לאחר שיתוף בלוקים או snapshots.

המדידות הן תמונת מצב תוך כדי פעילות recorder, ולא snapshot אטומי. הן אינן כוללות את כל `.git`, גיבויים או runtime משותף. ה־runtime המשותף עצמו תפס כ־20 MB בעת הבדיקה; התור הכיל 30 רשומות וכ־2.3 MB טקסט, כולל נתונים לפרויקטים חסרים. אין למחוק תור זה כחלק מניקוי לוגים.

ב־worktree הגדול של PoCut נמצאו:

- 274.0 MB בקובצי פעילות: 25,757 קובצי `activity.batch`.
- 92.0 MB ב־88 רשומות `task.evidence`, בעיקר מפות snapshot מלאות של קבצים ו־hashes.
- בתוך הפעילות, ייצוג JSON מקודד מחדש של רשומות `files.changed` תפס כ־232.4 MB. היו 440 רשומות עם יותר מ־1,000 נתיבים, והשיא היה 6,908 נתיבים ברשומה. זהו מדד לשדות בתוך הרשומות, שאינו כולל את כל מעטפת הקבצים.
- בשלושת עותקי PoCut נספרו 75,835 עותקי קובצי אירועים, לעומת 27,568 שמות אירועים שונים באיחוד. ל־23,563 שמות היה עותק בכל שלושת ה־worktrees. זו עדות לשכפול רחב של אותה היסטוריה; לא בוצעה השוואת תוכן מלאה לכל שם.

בכונן החיצוני קובצי JSON קטנים רבים מקבלים הקצאה של כ־128 KiB לקובץ, כולל קובצי AppleDouble. כך כמות הקבצים מייצרת עלות גבוהה בהרבה מגודל הטקסט. אין צורך להניח שאותה הקצאה חלה גם על הכונן הפנימי.

מקורות בקוד: `src/core.js` שומר אירועים ב־`.dip/events` ומנהל outbox; `src/automation.js` אוסף נתיבי watcher ומוסיף את `.dip` ל־index ב־pre-commit; `src/util.js` בונה snapshot עם מפת hashes מלאה. שלוש ההתנהגויות נשארות גם בגרסה המאוחרת. מגבלת cache בזיכרון אינה מגבלת ledger בדיסק.

## למה נוצרים קונפליקטים

כיום לכל worktree יש `.dip` משלו, והיא חלק מעץ הקוד. בהחלפת ענף אפשר לקבל קבצים משתנים, גרסאות config שונות, היסטוריה שאינה קיימת בענף החדש או שינויים מקומיים שמפריעים ל־checkout. ה־pre-commit גם מבצע `git add -- .dip` אוטומטית.

בנוסף קיימים קונפליקטים סמנטיים מכוונים: שתי פעולות בלתי תלויות משנות אותו שדה במשימה לערכים שונים. כבר קיימת בדיקה שממזגת ענפי Git בהצלחה, ובכל זאת מצפה ש־DIP ידווח על מחלוקת כזו. תכנון חדש צריך להסיר התנגשויות אחסון, ולשמור על מחלוקות אמיתיות במקום לבחור אוטומטית את העדכון האחרון.

ה־runtime כבר מזהה משפחת worktrees באמצעות Git common directory. לכן יש בסיס טוב למאגר משותף. לא נמצאה בבדיקה הוכחה לערבוב נתונים של פרויקטים עצמאיים; ההפרדה ביניהם צריכה להיות תנאי מפורש בתכנון.

## מבנה האחסון המוצע

| שכבה | מיקום מוצע | מדיניות |
|---|---|---|
| קוד ומדיניות בדיקות | ענפי הקוד | קוד, מסמכי תכנון, הוראות ו־verification configuration ששייכים לגרסת הקוד |
| מקור מקומי עמיד של DIP | תחת Git common directory, בספריית `dip/` | עותק אחד לכל משפחת worktrees; אירועים ו־outbox עמידים עם מזהים יציבים |
| סנכרון והיסטוריה משותפת | `refs/heads/dip/state` | ענף orphan יחיד, עם דרישות, החלטות, handoffs וראיות נחוצות; אין היסטוריית קוד כהורה |
| פעילות מפורטת | אחסון מקומי מרוכז | SQLite או segments סגורים ודחוסים; retention וגבלת נפח; לא מסונכרן כברירת מחדל |
| caches ותחזיות מצב | מקומי | ניתנים לבנייה מחדש; תקציב נפרד; אינם תחליף למקור העמיד או ל־outbox |

הפורמט של הנתונים העמידים צריך לאפשר פענוח מחדש ללא index מקומי. לא מכניסים קובץ SQLite משתנה ל־Git. אפשר להתחיל מאירועי JSON קומפקטיים למידע הסמנטי, ולהוסיף חבילות immutable עם אינדקס manifest כאשר מדידות מצדיקות זאת. בעת compaction יש לשמר IDs, קשרי הורות ויכולת לזהות היסטוריה חסרה.

קישורי Markdown ממשיכים להתייחס לקוד של ה־worktree הנבחר ול־hash שנבדק. מסמך שקיים בענף אחר לא יוצג בטעות כקובץ עדכני כאן.

### בחירת הענף

`dip/state` הוא הבחירה המומלצת לגרסה הראשונה: ענף נתונים orphan, רגיל מבחינת שרתי Git, אך DIP אינו מבצע אליו checkout. מעדכנים באמצעות Git plumbing ו־index זמני או בניית tree ישירה; אין שינוי של `HEAD`, ה־index, קבצים פתוחים או staging של המשתמש. אין ענף לכל task, session, worktree או ענף קוד. שמו הסופי ייקבע במימוש; ענף קיים באותו שם לא יידרס.

חלופה נקייה יותר מבחינת תצוגת ענפים היא `refs/dip/state`. היא דורשת fetch/push refspec מפורשים ובדיקת תאימות לכל שרת ואינטגרציה. היתרון שלה אינו מצדיק לגרסה הראשונה שינוי מקביל של כל צרכני GitHub. API האחסון צריך לאפשר מעבר אליה בעתיד.

מאגר Git נפרד לחלוטין מתאים לארגון שדורש הפרדת הרשאות או גיבוי, אך מוסיף ניהול repository וזהות. SQLite מקומי בלבד פשוט ומהיר, אך דורש מנגנון נוסף כדי לשחזר ולשתף intent ב־clone חדש. ענף ייעודי לכל ענף קוד משאיר שכפול ופיצול, ולכן אינו מומלץ.

### כתיבה וסנכרון

1. קבלה עמידה של הפעולה המקומית עם project ID, event ID, session וזהות מקור; אישור שמירה מקומית מופרד מאישור סנכרון.
2. כותב מקומי מתואם אחד לכל Git family מרכז עדכונים; גם עדכון ה־ref משתמש בהשוואה ל־OID הקודם כדי לא לדרוס כותב אחר.
3. מסנכרנים batches של metadata, ללא commit לכל קריאת כלי וללא Git lifecycle events חוזרים שנוצרים מעצם תחזוקת DIP.
4. כשמכשיר אחר הקדים: fetch מפורש לענף הנתונים, איחוד אירועים לפי ID, אימות הורים ו־payload, ואז ניסיון fast-forward נוסף. ID זהה עם תוכן שונה הוא שגיאה גלויה. אין force-push אוטומטי.
5. `parents` של אירוע משמרים את המצב שהכותב באמת ראה; אסור להמציא תלות סיבתית בין שינויים מקבילים רק משום שהסנכרון סידר commits ברצף.
6. כשל רשת משאיר outbox וסטטוס unsynced. מחלוקת סמנטית נשארת גלויה ומחייבת resolve. סנכרון Git אינו מעניק נעילת scope בזמן אמת בין מכונות; ההבטחה הקיימת נשארת מקומית.

השימוש ב־common directory וה־CAS תואם ל־[כללי worktree של Git](https://git-scm.com/docs/git-worktree#_refs) ול־[git update-ref](https://git-scm.com/docs/git-update-ref#_description). אלה מנגנוני בסיס מתועדים; פרוטוקול הסנכרון של DIP עצמו עדיין טעון מימוש ובדיקות.

## מודעות לכל הענפים

לכל אירוע נשמרים מקור הכתיבה: מזהה הפרויקט, מזהה worktree, שם ref מלא אם קיים, commit OID, session ומזהה פעולה. שומרים זאת בזמן התצפית, ולא מנחשים לפי הענף הפעיל בזמן flush. ב־detached HEAD משתמשים ב־OID; שם ענף הוא תווית שיכולה להשתנות או להיעלם.

רשימת ענפים ותצוגת היישום נגזרות מ־refs ומ־`git worktree list`. ברירת המחדל מציגה ענפים מקומיים ו־remote-tracking שכבר ידועים ל־clone; מידע משרת שאינו fetched לא מוצג כעדכני. לא נוצר ענף DIP נוסף בעת checkout, rename או מחיקת ענף קוד.

כוונת המשימה יכולה להיות גלובלית לפרויקט, אבל ראיות ויישום שייכים לגרסת קוד מסוימת. בדיקה מוצלחת ב־feature אינה הופכת את `main` לממומש או מאומת. שומרים סטטוס מימוש וראיות לפי snapshot/גרסת דרישות וענף התצוגה, ומחשבים integration מול ancestry והקוד הנוכחי. שינוי שם ענף או rebase לא גורם להשוואת שמות בלבד. מדיניות scope ownership המקומית הקיימת נשמרת עד לשינוי מפורש ונבדק שלה.

פרויקטים שונים מופרדים לפי זהות repository ו־project UUID; לא משתפים מאגר לפי שם תיקייה או שם ענף. clones עצמאיים של אותו פרויקט יכולים לסנכרן metadata, אבל אינם חולקים אוטומטית lease מקומי רק משום שיש להם אותו remote.

## מדיניות חיסכון מוצעת

המספרים הבאים הם ערכי פתיחה מוצעים לניסוי, לא מגבלות קיימות או תוצאות שנמדדו.

- פעילות מפורטת: עד 7 ימים ועד 32 MiB לכל פרויקט, לפי המגבלה שמגיעה ראשונה. תקציב גלובלי התחלתי של 256 MiB לפעילות מכל הפרויקטים, עם פינוי הישן ביותר ותיעוד retention. תקציב נשמר גם בזמן תקלה, ללא המתנה לשעון TTL בלבד.
- שגיאות וכשלים חשובים מקבלים סיכום עמיד במשימה לפני שרישום הביצוע המפורט מתיישן. אין פינוי אוטומטי של דרישות, תוכניות, החלטות, handoffs, ראיות נחוצות או intent שלא סונכרן.
- מאחדים פעילות שגרתית לפי operation ID: זמן התחלה/סיום, כלי, תוצאה ונתיבים רלוונטיים; לא משכפלים אותו command פעמיים. pending commands נשארים ניתנים לזיהוי לאחר crash. אין סינון סמנטי באמצעות מודל נוסף.
- שומרים שינויי קבצים כהפרש, ולא רשימות של אלפי נתיבים שחוזרות בעקבות checkout. פעילות Git מזוהה במפורש; אם אי אפשר להבדיל בבטחה בינה לבין עריכה אמיתית, שומרים סיכום מוגבל עם count/hash וסימון overflow. אין להציגו כרשימת שינויים מלאה.
- מפות snapshot גדולות נשמרות פעם אחת לפי content hash. ראיית הבדיקה מפנה אליהן ושומרת את fingerprint הדרישות, הפקודה, התוצאה וזהות המקור. hash לבדו אינו מספיק אם `task_changes` צריך השוואת קבצים היסטורית; manifest משותף חייב להישאר קריא. ברירת המחדל לראיות קיימות נשמרת בזמן migration, ללא צמצום שרירותי ל־scope צר יותר.
- budgets נמדדים גם לתוכן, למספר הקבצים, ל־WAL/DB, לאינדקסים ולמקום זמני של compaction. נדרש טיפול ב־SQLite page reuse/checkpoint ולא רק `DELETE` לוגי. גם logs ו־Trace2 דורשים rotation.
- `dip storage` ו־doctor יציגו חלוקה בין semantic ledger, raw activity, outbox, artifacts, caches והקצאת filesystem. ledger עמיד יכול לגדול עם היסטוריית העבודה; לא מבטיחים נפח סופי קבוע כאשר שומרים intent לעד. התראות וייצוא ארכיון מתועדים עדיפים על מחיקת דרישות בשקט.
- מצב audit מפורט יהיה opt-in עם תקציב ויעד ארכיון מפורשים. שמירת כל הפעולות לנצח מחייבת נפח שהולך וגדל.

ה־32 MiB הם תקציב לפעילות, לא הבטחה שכל Git repository או כל נתוני DIP יישארו מתחת לערך זה. יש להגדיר בנפרד overhead זמני מותר ולמדוד הקצאה בפועל בכונן עם clusters גדולים.

## מעבר בטוח מהפורמט הקיים

1. מצב אבחון בלבד: inventory של כל ה־worktrees במשפחה, dirty/untracked events, refs רלוונטיים, תורים, versions וצרכנים. גיבוי בר שחזור עם manifest וסיכומי ספירה/hash. ארכיון גיבוי מרוכז כדי לא לשכפל שוב עשרות אלפי קבצים קטנים.
2. הוספת storage interface וקורא legacy. קורא v2 יכול לייבא v1; כותב ישן חייב לקבל הודעה על הפורמט החדש במקום לייצר מחדש `.dip/events`. נדרש שער גרסה מוקדם גם בפתיחת ענף קוד ישן. אם אי אפשר להבטיח זאת בהתקנה נתונה, המעבר נחסם עד לעדכון כל הכותבים.
3. יבוא idempotent מכל העותקים הידועים, עם איחוד לפי ID ואימות תוכן, הורים, tasks, documents, conflicts וראיות. אין להסתפק בעותק `main`, משום שיש intent שלא מוזג מענפים אחרים.
4. מעבר נקודתי למאגר המשותף לאחר נעילה קצרה וחידוש outbox עם fencing מתאים. אין dual-write קבוע. תורים ישנים ממופים לזהות הפרויקט ומקור הענף; attribution חסר נשאר מסומן כלא ידוע.
5. הפרדת config: פקודות בדיקה ומדיניות התלויות בקוד נשארות versioned עם הקוד; העדפות capture ואחסון משותפות אינן נכתבות שוב לכל worktree. קובצי הוראות ו־skills סטטיים יכולים להישאר בענפי הקוד; מחלוקות אמיתיות בעריכתם עדיין אפשריות.
6. עדכון כל הצרכנים: CLI/MCP, hooks, recorder, doctor, dashboard מקומי, navigation/search, semantic prototype, portable helper, exporter וגיבוי. הדשבורד המתארח כיום קורא וכותב `.dip/events` בענף קוד נבחר, ולכן חייב להפריד בין ענף נתונים לבין ענף קוד בתצוגה לפני הפעלה מלאה.
7. רק לאחר השוואת התוכן והרצה מבודדת: הוצאת האירועים הדינמיים מהמעקב בענפי קוד פעילים, דרך migration commits מפורשים שמשמרים שינויים מקומיים. ענפים ותיקים שעדיין מכילים v1 יטופלו בעת כניסה ולא ב־checkout גורף. פרויקטים אחרים לא יעודכנו כחלק מ־migration של repository אחד.

הסרת קבצים מה־HEAD אינה מקטינה היסטוריית Git קיימת. גם ענף נתונים עצמאי משתמש באותו object database. Git ממשיך לשמור אובייקטים שנגישים מענפים, tags או reflogs; ראו [git gc](https://git-scm.com/docs/git-gc#_notes). שחזור מקומי וחבילות גיבוי מחייבים מדידה נפרדת. שכתוב היסטוריה ו־force-push לצמצום העבר יהיו החלטה נפרדת, אחרי גיבוי ותיאום, ואינם חלק מהמעבר האוטומטי המוצע.

## שלבי פיתוח וקריטריוני קבלה

| שלב | תוצר | איך מתקבלת ההחלטה להתקדם |
|---|---|---|
| 1 | דוח storage, מדיניות capture מוגבלת ו־rotation לפעילות | workload קבוע מדגים עצירת גידול פעילות, כולל WAL ומקום זמני; intent/outbox נשמרים |
| 2 | מאגר מקומי משותף ו־storage interface עם importer | שלושה worktrees רואים אותן משימות ללא שכפול היסטוריה; מעבר ענפים אינו משנה index או יוצר קבצים דינמיים בענף הקוד |
| 3 | ענף `dip/state`, פרוטוקול sync ותצוגה לפי ענף | שני clones מסנכרנים עדכונים מקבילים בלי אובדן ובלי force; סתירות אמיתיות מדווחות; ענף נתונים אחד בלבד |
| 4 | manifests משותפים, migration לכל הצרכנים ופיילוט מוגבל | שוויון בדרישות, הורים, מסמכים וראיות לפני/אחרי; dashboard/portable וענפים ישנים פועלים לפי החוזה החדש |

בדיקות מהותיות: מעבר חוזר בין ענפים עם קבצים staged ובלתי שמורים; worktrees במקביל; detached HEAD, rename, rebase ו־cherry-pick; clone ללא ענף metadata מקומי; רשת מנותקת ו־push שנדחה; שתי כתיבות CAS מקבילות; crash לפני ואחרי ref update; כשל דיסק/הרשאה; source branch משתנה לפני flush; שגיאת ID זהה עם payload שונה; importer שמופעל פעמיים; כותב ישן לאחר migration; מחלוקת דרישה וראיה שאינה תקפה ב־main; שני פרויקטים עם אותו שם ענף שאינם חולקים מידע.

מדידת ביצועים תיקבע לפני המימוש: workload זהה עם checkout שמחליף כ־7,000 נתיבים, 100 פעולות בדיקה עם manifests חוזרים, שלושה worktrees ומשך שמפעיל retention. מדווחים את כל רכיבי הנפח, duplicate bytes, קובצי filesystem, queue durability, וזמני hooks ב־p50/p95. יעד התחלתי מוצע: ירידה של לפחות 80% בשכבת הפעילות והכפילויות לעומת אותו workload בגרסה הקיימת, בלי להפוך אותו להבטחה לכל פרויקט. אין צורך להריץ מודלים נוספים כדי לבדוק את מנגנון האחסון.

הסדר המומלץ הוא להתחיל בבלימת הגידול ובמאגר מקומי משותף, ואז להוסיף את ענף הסנכרון. כך כל שלב נותן תועלת מדידה, והפרדת הענפים אינה מסתירה בעיית נפח שנשארה פתוחה.
